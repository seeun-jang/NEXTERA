## 1. 무엇을 하는가

GPU 데이터센터에서는 과열과 마감 지연이 동시에 터집니다. 노드 하나를 식히려고 일을 옮기면 옮겨 간 노드가 뜨거워지고, 급한 일을 앞에 세우면 다른 일이 밀립니다. 단순한 임계값 규칙으로는 풀기 어렵고, AI에게 통째로 맡기기에는 위험합니다.

NEXTERA는 이 문제를 네 부분으로 나눕니다.

1. **코드가** 문제를 찾고, 규칙을 지키는 계획 후보를 만든다.
2. **Zoro-1이** 검증된 후보 중 하나를 고른다.
3. **모델과 분리된 코드와 사람이** 실행 전에 다시 확인한다.
4. **모든 과정을** 결정 영수증으로 남긴다.

정해진 한 장면이 아니라, 운영자가 노드(1~6개)와 일(1~10개)을 직접 정해 여러 상황을 바로 시험할 수 있습니다.

## 2. 전체 흐름

```
상황 설정 → 문제 찾기 → 계획 후보 생성 → Zoro-1 선택 → 안전 검사 → 역할별 승인 → 가상 실행
                ↑                                                                        │
                └────────────── 남은 문제가 있으면 다음 회차 (최대 4회차) ───────────────┘
                                풀 수 없으면 멈추고 사람에게 넘김
```

| 단계 | 화면 | API | 하는 일 |
|---|---|---|---|
| 상황 설정 | 상황 설정 | `POST /api/v2/scenario` | 노드·냉각 구역·일을 받아 검증하고 초기 상태를 만든다 |
| 상황 파악 | 운영 현황 · 사건 상세 | `GET /api/v2/state` | 조치 없이 두면 생기는 사건을 찾아 급한 순으로 정렬한다 |
| 판단 | 운영 정책 · 의사결정 센터 · 대안별 결과 | `POST /api/v2/decide` | 계획 후보를 만들고 Zoro-1이 하나를 고른다 |
| 통제된 실행 | 안전 검사 · 협업·승인 · 실행 결과 | `POST /api/v2/validate` · `approvals` · `execute` | 다시 검사하고, 승인을 받고, 가상으로 실행한다 |
| 결정 영수증 | 결정 영수증 · 기록·분석 | `GET /api/v2/receipt` · `/api/v2/log` · `/api/analytics` | 회차별 기록과 집계를 보여 준다 |


## 3. 알고리즘

### 3.1 상황과 발열 모델

- 노드당 GPU 8장, 일은 노드당 최대 4개. 냉각 구역 하나가 노드 2개를 맡고 냉각 레벨은 최대 5입니다.
- 한 노드에서 GPU 합이 8장 이하면 동시에 실행하고, 넘으면 그 노드에서 대기합니다.
- 노드 온도는 목표 온도를 향해 움직입니다.

```
목표 온도 = 40 + 6.25 × 실행 중 GPU 수 × (팬 이상이면 1.5) − 6 × 냉각 레벨   (최저 38°C)
목표와의 차이는 4분마다 약 63%씩 줄어든다
```

- 85°C 이상이면 처리 속도가 0.7배로 느려지고, 88°C가 안전 한계입니다.
- 옮기거나 멈춘 일은 재시작에 1분이 더 듭니다.
- 예측은 30초 간격으로 30분을 시뮬레이션합니다. 같은 입력이면 항상 같은 결과가 나옵니다.

### 3.2 사건 찾기

조치 없이 30분을 시뮬레이션해 두 종류의 사건을 찾습니다.

- **과열 위험**: 88°C 이상이 되는 노드
- **마감 위험**: 마감 안에 끝나지 못하는 일

한계까지 남은 시간이 짧을수록, 일의 우선순위(P0 > P1 > P2)가 높을수록 위에 놓습니다.

### 3.3 계획 후보 생성

후보 하나는 행동 하나가 아니라 **행동 여러 개로 된 계획**입니다. 행동은 다섯 가지입니다.

| 행동 | 내용 |
|---|---|
| 떠맡기기 | 일을 다른 노드로 옮긴다 |
| 새치기 | 일을 옮겨 맨 앞에 세운다. 필요하면 덜 급한 일을 멈춘다 |
| 임시 대피 | 노드가 식을 때까지 일을 잠시 다른 곳에 둔다 |
| 연기 | 급하지 않은 일을 30분 미룬다 |
| 냉각 변경 | 구역의 냉각 레벨을 바꾼다 |

만드는 순서는 다음과 같습니다.

1. 전략 8종(냉각 우선, 열 분산, 마감 우선, 저우선 연기, 임시 대피, 구역 몰기, 에너지 최소, 조작 최소)에 변형과 혼합을 더해 **56가지 방법**을 준비한다.
2. 각 방법이 "가장 급한 사건 → 행동 1개 → 시뮬레이션"을 사건이 없어질 때까지 반복해 계획을 만든다.
3. 빼도 결과가 같은 단계를 지우고, 결과가 같은 계획을 합친다.
4. **Safety Gate**: 규칙을 어기거나 새 사건을 만드는 계획을 뺀다.
5. 모든 면에서 다른 계획에 뒤지는 계획, 아무 사건도 못 푸는 계획을 뺀다.

"사건이 동시에 터진 날" 상황의 실제 숫자는 56 → 48 → 29 → 15 → 15이고, 그중 상위 5개가 Zoro-1에 전달됩니다.

전수 탐색이 아니라 전략으로 만든 계획 중에서 고르는 방식입니다. 후보 생성은 이 상황에서 약 0.2초가 걸립니다.

### 3.4 필수 규칙

어떤 승인으로도 풀리지 않는 규칙입니다. 후보를 만들 때, 안전 검사 때, 실행 직전에 같은 코드로 검사합니다.

| 규칙 | 내용 |
|---|---|
| POL-01 | P0 일은 옮기거나 연기하거나 멈추지 않는다 |
| POL-02 | 88°C 이상의 과열을 새로 만들거나 악화시키지 않는다 |
| POL-03 | 대상 노드에 자리가 있어야 한다 |
| POL-08 | 계획 때문에 마감을 놓치는 일이 생기지 않는다 |
| POL-09 | 더 급한 일만 다른 일을 멈출 수 있다 |
| COOL-MAX | 냉각 레벨은 구역 상한을 넘지 않는다 |

### 3.5 Zoro-1의 판단

- 검증된 후보 중 규칙 순위 상위 5개를 선택지로 줍니다.
- 질문은 두 가지입니다: 어느 계획을 고를지(선택형), 지금 상황이 얼마나 위험한지(점수형).
- **같은 후보를 순서만 바꿔 4번 묻습니다**(원래 순서, 뒤집은 순서, 섞은 순서 두 번). 가장 많이 1위였던 계획을 고르고, 같으면 평균 확률로 정합니다.
- 1위와 2위의 확률 차이가 0.05 미만이거나 1위 횟수가 절반 이하면 화면에 "검토 권장"을 표시합니다.
- Zoro-1은 미세조정 없이 그대로 사용했습니다.

### 3.6 통제된 실행

- **안전 검사**: Zoro-1이 고른 계획도 모델과 분리된 코드가 단계마다 다시 검사합니다. 운영자가 규칙을 어기는 행동을 강제로 넣어도 같은 검사를 거쳐 차단됩니다.
- **역할별 승인**: 냉각 변경은 냉각 담당(A), 일 이동은 GPU 담당(B)이 승인합니다. 권한 없는 승인은 화면의 버튼과 서버 양쪽에서 막습니다.
- **실행 직전 재검사**: 승인 이후 상태가 바뀌었는지와 규칙을 한 번 더 확인하고, 실패하면 적용하지 않습니다.
- 실행은 가상 환경에서만 합니다. 실제 설비는 제어하지 않습니다.

### 3.7 회차 반복과 사람에게 넘김

실행 직후의 상태에서 남은 사건을 다시 계산합니다.

| 상태 | 다음 |
|---|---|
| 남은 사건 없음 | 끝 |
| 남았고 진전이 있음 | 다음 회차 (최대 4회차) |
| 진전이 없음 · 최대 회차 도달 · 안전한 계획 없음 | 멈추고 사람에게 넘김 |

어떤 계획으로도 풀 수 없는 사건은 따로 표시해 사람에게 넘기고, 풀 수 있는 사건만 계획으로 풉니다.

## 4. 차별점

**1. 한 계획이 여러 사건을 함께 풉니다.**
사건마다 따로 행동을 고르면 서로 부딪힙니다. NEXTERA는 여러 행동을 이어 붙인 계획 단위로 만들고 통째로 시뮬레이션해서, 과열 두 곳과 마감 위험 하나를 계획 하나로 해결합니다.

**2. Zoro-1은 검증된 후보 안에서만 고릅니다.**
규칙을 어기는 계획은 모델에 전달되지 않습니다. 모델이 무엇을 고르든 필수 규칙을 어길 수 없습니다.

**3. 후보 순서에 따른 흔들림을 줄였습니다.**
후보 순서를 바꾸면 모델의 1위가 달라지는 것을 실제로 확인했습니다. 제출한 실행 로그에서도 "사건이 동시에 터진 날"은 원래 순서에서 P02, 나머지 세 순서에서 P03이 1위였습니다. 그래서 순서를 바꿔 4번 묻고 다수결로 정하며, 몇 번 일치했는지를 화면과 로그에 그대로 보여 줍니다.

**4. AI가 골라도 바로 실행되지 않습니다.**
독립된 안전 검사, 역할이 나뉜 두 사람의 승인, 실행 직전 재검사를 모두 통과해야 실행됩니다.

**5. 풀 수 없으면 멈춥니다.**
안전한 계획이 없으면 무리해서 실행하지 않고 사람에게 넘깁니다. 이때는 Zoro-1도 호출하지 않습니다.

**6. 오류가 나도 흐름이 이어집니다.**
Zoro-1 호출이 실패하면 규칙 순위 1위로 대신 고르고, 대신 골랐다는 사실과 이유를 화면과 기록에 남깁니다.

**7. 모든 결정을 추적할 수 있습니다.**
회차마다 사건, 후보, Zoro-1에 보낸 요청과 받은 응답, 승인, 실행 결과, 차단된 시도를 남깁니다.

## 6. 시연 방법

**직접 조작**: 첫 화면에서 시작해 상황 설정 → 사건 → 판단 → 안전 검사 → 승인 → 실행 → 결정 영수증 순서로 진행합니다. 준비된 상황은 네 가지입니다.

| 상황 | 볼 수 있는 것 |
|---|---|
| 기본 상황 | 과열 하나를 푸는 기본 흐름 |
| 사건이 동시에 터진 날 | 사건 3건을 계획 하나로 해결, A·B 두 역할의 승인 |
| 옮길 자리가 없는 날 | 모든 노드가 꽉 차 옮길 수 없을 때의 선택 |
| 손쓸 수 없는 문제가 섞인 날 | 2회차에서 멈추고 사람에게 넘김 |

**자동 시연**: 주소 뒤에 `?tour=1`(발표용 약 2분) 또는 `?tour=full`(제출용 긴 판)을 붙이면 실제 화면을 따라가며 자막으로 설명합니다. 서버의 실제 응답을 읽어 자막을 맞춥니다.

**시연 영상**: 첫 화면의 "시연 영상 보기 (2분)"로 녹화본을 볼 수 있습니다. 영상 속 판단 값은 실제 Zoro-1 응답이며, 데모 서버에서 받은 응답을 같은 코드에 재생해 녹화했습니다.

## 7. 직접 실행하기

### 모델 없이 (규칙 모드)

GPU와 모델이 없어도 전체 흐름을 볼 수 있습니다. 판단만 규칙 순위로 대신합니다.

```bash
cd frontend && npm install && npm run build
cd ../backend && pip install -r requirements.txt
NEXTERA_PROVIDER=rule python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

브라우저에서 `http://localhost:8000`을 엽니다. 백엔드가 빌드된 화면까지 함께 내보냅니다.

### Zoro-1과 함께


```bash
export NEXTERA_PROVIDER=zoro1_local
export ZORO1_SNAPSHOT_DIR=<Zoro-1 모델 폴더>
cd backend && python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

| 환경 변수 | 뜻 |
|---|---|
| `NEXTERA_PROVIDER` | `zoro1_local`(모델 직접 로드) · `zoro1`(Zoro-1 서버 호출) · `rule`(규칙만) |
| `ZORO1_SNAPSHOT_DIR` | `zoro1_local`일 때 모델 폴더 |
| `ZORO1_URL` | `zoro1`일 때 서버 주소 |

### 테스트

```bash
cd backend && python -m pytest -q        # 48개
```

## 9. 대회 조건과 한계

**대회 조건**

- 판단(System 1)은 Zoro-1이 합니다.
- 미세조정을 하지 않았습니다.
- 실제 설비를 제어하지 않습니다. 모든 실행은 가상입니다.

**한계**

- 온도, 에너지, 완료 시간은 모두 시뮬레이션 값입니다. 발열 모델은 시연용으로 단순화한 것이고 실제 장비의 측정값이 아닙니다.
- 계획 후보는 전략으로 만든 것 중에서 고릅니다. 가능한 모든 계획을 탐색하지 않으므로 최적을 보장하지 않습니다.
- Zoro-1에는 규칙 순위 상위 5개만 전달합니다.
- 기록·분석 화면은 지금 접속한 브라우저 탭의 현재 시연만 집계합니다.
