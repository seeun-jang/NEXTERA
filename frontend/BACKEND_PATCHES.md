# 프론트 v12에 적용한 백엔드 연동 패치

v12(`nextera_fe_v12.zip`)의 `src`를 그대로 쓰고 아래만 고쳤다. 타입 검사(`tsc`)는 통과했다. 빌드와 브라우저 확인은 Brev에서 한다.

| 파일 | 바꾼 것 | 이유 |
|---|---|---|
| `src/api/client.ts`, `src/api/v2.ts` | `VITE_API_MODE`를 주지 않으면 빌드본은 live, 개발 서버는 mock. 빌드본의 기본 주소는 같은 서버(`/api`) | 백엔드가 `dist`를 직접 서빙하므로 환경 변수 없이 `npm run build`만 하면 연결된다 |
| `src/api/v2.ts` | 상황을 보낼 때 노드의 `fan`(팬 이상)도 보냄 | 서버가 프론트와 같은 발열 식(팬 이상 1.5배)으로 계산한다. 프리셋의 사건이 서버에서도 똑같이 나온다 |
| `src/api/v2.ts` | 후보의 `temps` → 계획별 온도 곡선, `no_action.cooling_kwh` → 조치 없음 에너지, JSON이 아닌 응답 처리 | 06 대안별 결과의 차트와 에너지 칸이 채워진다 |
| `src/sim/engine.ts` | `Analysis`에 선택 필드 추가: `provider`, `fallbackReason`, `probs`, `offered`, `agreement`, `needsReview`, `latencyMs` | 서버 판단의 출처와 확률을 화면까지 싣기 위한 자리. mock 엔진에서는 비어 있다 |
| `src/state/run.tsx` | 서버 응답의 깔때기 수치(`decision.stats`), 탈락 계획(`rejected`), 위 필드를 채움 | 04 운영 정책의 깔때기와 사람에게 넘김 화면의 탈락 사유가 서버 값으로 나온다 |
| `src/pages/DecisionPage.tsx` | 출처 칩을 응답의 `provider`로 표시(기존에는 항상 MOCK), 후보별 확률, "Zoro-1 선택 / 규칙 선택 / 모의 선택" 구분, Zoro-1에 주지 않은 후보 표시 | live에서 실제 Zoro-1 응답인데도 MOCK으로 보이던 것을 바로잡는다 |
| `src/pages/ApprovalPage.tsx` | 출처 칩을 응답의 `provider`로 표시 | 위와 같음 |
| `src/pages/DecisionPage.tsx` | 후보 목록을 "Zoro-1에 전달한 후보"와 "전달하지 않은 후보" 두 구역으로 나눔 | 화면에 10개가 한 목록으로 보여 10개를 다 전달한 것처럼 읽혔다 |
| `src/pages/ReceiptPage.tsx`, `src/api/v2.ts`, `src/state/run.tsx` | 결정 영수증에 "누적 기록" 구역 추가(`GET /api/v2/history`). 상황을 보낼 때 프리셋 이름도 함께 보냄 | 새 시연을 시작하면 지난 결과가 사라지던 것을, 접속자별 최근 10건까지 쌓이게 함 |
| `src/pages/AnalyticsPage.tsx` | 실행 결과를 "성공 · 실패" 두 가지로. 실패 = 안전한 계획이 없어 실행하지 못하고 사람에게 넘긴 결정(기존 "보류"). 결과 필터도 "전체 · 성공 · 실패" | 기존 "실패"는 해당 조건이 없어 항상 0이었다 |
| `src/pages/AnalyticsPage.tsx` | 시나리오 필터 항목을 "과열 위험 · 마감 위험"으로 바꾸고, 필터를 "최근 결정" 표에도 적용 | 기존 항목(승인 지연 등)은 새 흐름에 없는 분류라 골라도 아무 일도 일어나지 않았다 |

| `src/pages/PoliciesPage.tsx`, `src/pages/ScenarioPage.tsx` | 문구: "상위 N개를 Zoro-1에 전달", "팬 이상 포함으로 서버가 다시 계산" | 서버 동작과 맞춤 |

## 규칙은 백엔드 기준 (프론트 엔진을 맞춤)

프론트 엔진(`src/sim/engine.ts`, mock 모드와 상황 설정 미리보기에 쓰임)의 규칙 세 가지를 백엔드와 같게 고쳤다.

| 규칙 | 프론트 v12 원본 | 백엔드 기준 (적용) |
|---|---|---|
| 연기 | P2 일만 가능(POL-06) | P0만 아니면 가능. 낮은 우선순위부터 시도 |
| 이미 한계 이상인 노드 | 시작 온도가 88°C 이상이면 어떤 계획으로도 "과열"이 풀리지 않음 | 2분 안에 한계 아래로 내려오고 그 뒤 다시 넘지 않으면 풀린 것으로 봄 (`RECOVER_MIN`) |
| 줄 서기 | 앞의 일이 못 들어가면 뒤의 일도 전부 대기 | 못 들어가는 일만 대기. 뒤의 작은 일이 빈자리에 들어갈 수 있으면 먼저 실행 |

`src/pages/ValidatePage.tsx`의 연기 검사 문구도 "P0 제외 · 30분 이내"로 바꿨다.
계산식(평형 온도, 팬 이상 1.5배, 시간상수, 예측 구간, 냉각 에너지)은 반대로 백엔드가 프론트 값을 따른다.

## 서버 동작 (요약)

- 호출 규격은 `backend/MULTI_API.md`. 프론트의 `FRONT_V2_NOTE.md`에 적힌 필드는 모두 온다.
- 발열 계산·사건 정렬·예측 구간(30분)은 프론트 엔진과 같게 맞췄다. 규칙(연기, 줄 서기)은 위 표대로 백엔드 기준이다.
- 화면에는 검증된 후보 전부(최대 24개)가 오고, Zoro-1에는 규칙 순위 상위 5개만 선택지로 준다. 같은 후보를 순서만 바꿔 4번 묻고 가장 많이 1위였던 계획을 고른다.
- 다음 회차는 계획을 적용한 직후의 상태에서 남은 문제를 다시 본다.
- 의견(코멘트)은 서버 엔드포인트가 없어 프론트 기록에만 남는다. 첫 화면은 기존 `/api/state`를 부른다.
- 기록·분석 화면은 기존 `/api/analytics`, `/api/receipts`를 부르고, 서버가 여기에 다중 작업 기록(회차별 결정, 차단, 사람에게 넘김, 실행 결과)을 합쳐 돌려준다. 예시 값은 없다.
